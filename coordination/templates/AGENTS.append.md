# 项目协作规则（合并用片段）

使用方法：先阅读项目已有的 `AGENTS.md` 和相关说明，再合并本片段。
保留已有的有效约束；按项目实际情况处理重复或冲突，不直接覆盖原文件。
本模板约定协作方法，本身不会自动创建会话、启动任务或连接其他工具。

## 任务从哪里来

- 每项工作使用唯一任务编号，例如 `T001`。
- 开工前读取对应任务文件，确认需求版本、目标、范围和验收条件。
- 聊天里出现影响范围或验收的新决定时，先同步到任务文件，再继续受影响的工作。
- 未涉及歧义的常规实现选择，由执行者自行处理，无需逐项询问用户。

## 执行者的职责

- 按需求编号实现功能，不能悄悄删除、降低或延期必需项。
- 遇到缺信息、缺访问或实现限制时，保留原要求并记录具体阻塞。
- 验证应针对实际风险和验收条件；不强制每次运行全量测试。
- 已有有效测试可以复用；必要时补充能发现真实错误的测试或实际运行检查。
- 如实记录实际运行的命令、结果及证据；未运行的检查不得写成通过。
- 完成后使用结果模板，逐项报告；“已实现”不等于“已通过审核”。

## 审核者的职责

- 读取原任务、实际代码和执行报告；不能只依据执行者的文字总结判断。
- 独立核查每个必需项，必要时运行有意义的验证。
- 审核者可以写审核报告，无权悄悄修改需求、验收标准或产品代码。
- 将发现的问题交还执行者；需要变更需求时，提出明确建议供有权决定者处理。
- 没有足够证据的条目标记为“待验证”或“阻塞”，不能判定通过。

## 版本与证据

- 执行报告和审核报告都要记录需求版本及实际检查的代码版本。
- 使用 Git 提交号时，说明是否还有未提交或未跟踪的相关文件。
- 如存在这些文件，提供包含实际代码的可复现快照；仅写 `HEAD` 不足以定位它们。
- 代码变更后，重新核查受影响项；旧版本的审核不能自动用于新版本。
- 报告可写入独立的结果目录，避免为了记录报告而改动被审核的产品代码。

## 返工与收尾

- 建议默认最多自动返工 2 轮；实际次数、预算和触发方式按具体任务约定。
- 每轮围绕未通过项修复，完成后再审核受影响项及必要的回归行为。
- 达到上限仍未解决时，集中报告卡点、已有证据和需要决定的事项。
- 只有所有必需项都有足够证据且审核通过，才能将任务标记为已通过。
- 发布、合并及设备执行等后续动作，沿用项目已有授权和流程。
