## 已确定的约束

- 先检查 Git 工作区并保留既有改动。只更新上述任务分支；不强制推送，不直接推 main。

- 本次唯一新增并提交的文件是 `coordination/tasks/T001/RESULT.md`。使用明确路径暂存，避免提交无关文件或本机运行状态。
- 缺 GitHub 推送认证时，使用本机已有授权或标准登录流程；若无法完成，报告具体阻塞。不要在聊天或仓库中填写 token。

## 执行步骤

1. 核对 origin 指向本仓库，获取远端任务分支并在合适的工作副本中执行。报告时不要输出 remote URL 中可能存在的凭据。
2. 读取 `AGENTS.md` 和本任务；记录开始执行时的提交 SHA、本任务文件 SHA256、相关未提交改动是否存在。
3. 在本机直接读取 `coordination/connection-check.md`，确认检查标记，并计算文件的实际 SHA256。
4. 按下面的最小报告要求创建 `RESULT.md`，填写实际观察到的值；不要直接复制预期值当作执行结果。
5. 检查改动差异，只提交 RESULT.md，推送到 `origin/task/T001-github-handoff`。不进行自动合并。
6. 推送后读取远端分支头，确认它与本地交付提交一致。在聊天中返回任务编号、分支、完整交付 SHA、RESULT.md 的该提交版本链接及是否有剩余相关改动。

## RESULT.md 最小内容

- 任务编号和需求版本。
- 开始执行的提交 SHA、任务文件 SHA256、任务分支。
- 检查文件的实际标记与 SHA256。
- 实际执行的检查/命令类别及结果；避免发布账号信息、绝对私有路径或完整环境变量。
- R1 至 R4 的逐项执行结果及证据；R5 明确留给 ChatGPT 审核。
- 开始和交付时是否存在相关未提交改动；如有，描述范围并说明没有覆盖或混入本次提交。
- 未完成项或阻塞；没有则写无。

报告记录它所检查的起始版本，不填写包含报告自身的最终提交 SHA。最终 SHA 在提交后通过 Codex 的聊天回执给出，避免为了更新报告而不断生成新提交。

## 审核与返工

审核者按回传的交付 SHA 读取本任务、检查文件和报告，并检查提交差异。它能独立确认 GitHub 中的版本、文件内容、哈希和范围；本机命令执行及账号使用情况属于回传证据，未亲自运行时必须注明。此次通过仅代表任务交接成立，不代表网页直读本机文件或自动多 agent 调度已经完成。

若发现问题，记录具体条目供下一轮修复；建议最多 2 轮。当前由用户消息触发下一阶段，未部署自动调度。
